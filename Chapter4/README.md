# 第 4 章：性能测量与高速缓存

第 3 章用渐近记法讨论“工作量随规模怎样增长”。本章进一步问：**同样的工作量，为什么实际时间可能差很多？**先看简单计算机模型，再用可手算的缓存模型和实际遍历实验理解缓存未命中，最后学习怎样设计可靠的计时实验。

## 1. 简单计算机模型能说明什么

分析算法时，我们常假定一次整数加法、比较、数组访问都花常数时间。因此扫描 `n` 个元素是 `Θ(n)`，扫描 `n×n` 个元素是 `Θ(n²)`。这个模型适合比较增长趋势，但它把“数组访问”简化得太多：真实计算机取数据可能从离 CPU 很近的缓存中取得，也可能要到更远的主存（DRAM）读取。

```text
CPU 核心 → L1 缓存 → L2 缓存 → 最后一级缓存 → 主存
          小且快      更大、更慢                    大但更慢
```

这里的“命中”是指所需数据已在当前检查的缓存层；“未命中”会继续查下一层。若一直没命中，必须从主存取回。各层并非一次只搬一个 `int`，而是按**缓存行**搬运相邻的一块数据。许多现代 CPU 使用 64 字节缓存行，但实际硬件参数应以所用机器为准。[Intel 的缓存与局部性说明](https://www.intel.com/content/www/us/en/developer/articles/technical/loop-optimizations-where-blocks-are-required.html) 介绍了分层缓存、缓存行和主存访问。

两种局部性决定程序能否用好刚取到的数据：

- **空间局部性：** 访问 `a[i]` 后，很快访问相邻的 `a[i+1]`；它们可能已经在同一缓存行。
- **时间局部性：** 刚访问过 `a[i]`，不久又访问它；若尚未被淘汰，可以复用。

缓存容量有限。访问的新数据会逐步挤掉旧数据；随后再访问被挤掉的地址，就会重新未命中。**未命中不表示数据丢失或程序出错，只表示较近的缓存暂时没有所需内容。**

## 2. 一个能手算的 4×4 例子

`cacheDemo.cpp` 先模拟一个很小的缓存：行主序的 `int a[4][4]`，每条缓存行恰好装 4 个 `int`（即一整行），缓存只能容纳 2 条缓存行，满时淘汰最久未使用的行（LRU）。开始时缓存为空。

```text
内存布局：a[0][0..3] | a[1][0..3] | a[2][0..3] | a[3][0..3]
缓存行：      0             1             2             3
```

| 顺序 | 前几次访问的缓存行 | 16 次元素访问中的命中 / 未命中 |
| --- | --- | --- |
| 行优先：一行读完再读下一行 | `0,0,0,0,1,1,1,1,...` | 12 次命中，4 次未命中 |
| 列优先：一列读完再读下一列 | `0,1,2,3,0,1,2,3,...` | 0 次命中，16 次未命中 |

行优先访问某行的第一个元素时取入整条缓存行，后面三个元素直接命中。列优先在再次访问同一行之前已经访问另外三行；只有两行容量，所以那条缓存行早被淘汰。**两个算法都访问相同的 16 个元素、做相同的 16 次加法，区别是数据是否来得及复用。**

这是刻意简化的模型，不是对真实 CPU 缓存大小或淘汰策略的声明。真实 CPU 还会有多级缓存、预取、乱序执行、TLB 等机制。

## 3. 未命中怎样影响时间

在简化的**串行访问**模型里，可以用下面的式子建立直觉：

```text
平均一次访问时间 ≈ 命中时间 + 未命中率 × 额外未命中代价
```

例如假设命中花 1 个时间单位，未命中额外花 100 个单位，那么未命中率 1% 时平均约 `1 + 0.01×100 = 2`；未命中率 10% 时约 `11`。这只是**示意数字**，不能直接拿来预测某台机器的总运行时间。真实处理器可能提前取数、并行处理多个未命中，也可能因依赖下一次读数而停顿；还要算计算、分支和其他开销。

因此行优先和列优先完整扫描都属于 `Θ(n²)`，但实际耗时的常数可能差很多。渐近复杂度回答增长阶，缓存行为帮助解释同一增长阶内部的性能差异。

## 4. 实际遍历实验：保持问题相同

`cacheDemo.cpp` 的第二部分建立一个 2048×2048 的行主序 `int` 数组（若 `int` 为 4 字节，约 16 MiB）。`sumRows` 和 `sumColumns` 都恰好读取每个元素一次并求和，只改变访问顺序。程序核对两个总和相同，交替测量顺序，先热身两轮，再各取 7 次计时的中位数。

在行主序布局下，行优先通常有较好的空间局部性；列优先以较大步长访问，可能带来更多缓存和地址转换开销。实际快慢与差距取决于 CPU、缓存容量、编译器、预取器和系统负载；**计时差异本身不能精确证明发生了多少次硬件缓存未命中**。要测未命中事件，需要硬件性能计数器或性能分析器。可先比较程序输出，再回到上面的 4×4 模型解释原因。

## 5. 怎样设计排序计时实验

`time.cpp` 比较插入排序在三种同规模输入上的表现：

| 数据 | 构造方式 | 对插入排序的影响 |
| --- | --- | --- |
| 已排序 | `0,1,...,n-1` | 每轮很快停下，接近最好情况 `Θ(n)` |
| 逆序 | `n-1,...,1,0` | 每轮移动已有前缀，最坏情况 `Θ(n²)` |
| 随机排列 | 固定种子打乱同一组整数 | 便于重复实验；这**不是**未经定义输入分布的“平均情况证明” |

实验把规模设为 256、512、1024、2048，对每组输入先运行 3 次热身，再记录 25 次耗时并取中位数。每次计时前复制原始数据，**计时区间只包含排序**；计时后核对结果恰好是 `0..n-1`。复制会让输入较可能处于热缓存，因此这里测的是“复制后立即排序”的场景，不能当作冷缓存排序时间。

原来的 `insertionSort` 把外层循环变量 `i` 传给会修改长度的 `insert(a, i, t)`，使循环跳过元素。`insert.hpp` 已改为排序函数自己移动元素，计时前先保证排序正确。原计时还把重建逆序输入算在排序耗时里，并用固定的 1000 个 `clock()` 滴答控制循环；滴答频率依平台而异。新版使用 `std::chrono::steady_clock`，并把测试数据准备与正确性核对放在计时区间之外。

做自己的实验时，还应写清：编译优化选项、机器和编译器、输入生成方式、重复次数、报告统计量。控制后台负载；不要只测一次就下结论。若操作太快以至于与计时器开销同量级，应扩大规模或用更谨慎的批量测量方法。

## 6. 与大模型的“缓存未命中”类似吗？

**抽象思路类似：** 已经准备好的内容能够复用就是命中；没有命中就走更昂贵的路径。但“缓存什么”和“未命中后做什么”不同。

| 场景 | 缓存的内容 | 未命中时主要发生什么 |
| --- | --- | --- |
| CPU 数据缓存 | 主存中某些地址对应的缓存行 | 从更低一层缓存或主存取数据，可能让 CPU 等待 |
| 大模型生成时的 KV cache | 已处理 token 的注意力 key/value 状态 | 如果不能复用，要重新计算相应状态；也可能受显存空间与搬运策略影响 |
| 跨请求的提示词缓存 | 相同提示词前缀的已计算状态 | 重新处理未复用的输入前缀；后续新输入与输出仍需计算 |

例如两次提问都以同一段长的说明开头，第二次若命中提示词缓存，可以复用那段前缀的计算结果。若前缀改变或缓存不可用，就需要重新处理那部分输入。OpenAI Docs 将提示词缓存描述为复用相同前缀的 KV 状态，且新输入仍需处理；[官方提示词缓存文档](https://developers.openai.com/api/docs/guides/prompt-caching) 可查看具体机制。[Hugging Face 的 KV cache 文档](https://huggingface.co/docs/transformers/kv_cache) 则解释了逐 token 生成时如何复用已有注意力状态。

所以二者可以用“命中率与未命中代价”作类比，但 **CPU 缓存未命中主要是数据搬运问题；大模型提示词或 KV 缓存未命中主要意味着重复计算，有时也涉及显存搬运**。它不表示模型忘记了上下文，更不直接等同于回答错误。还要区分：逐 token 生成时复用当前请求历史状态的 KV cache，与跨请求复用共同前缀的提示词缓存，是相关但不同的使用场景。
