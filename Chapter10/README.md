# 第 10 章：字典、跳表与哈希表

本章用同一个字典接口对比五种存储结构：有序数组、有序链表、跳表、链地址散列和线性探查散列。仓库的 `Chapter9` 是队列，因此跳表与散列的现有代码保留在 `Chapter10`；下文按字典、跳表、散列和 LZW 的学习顺序讲解。

## 1. 字典是“做什么”，数据结构是“怎么做”

字典（dictionary）是一种抽象数据类型（ADT）：保存“键 → 值”数对，每个键最多对应一个值。它不是某一种具体链表或数组，也不一定按键排序。

例如学生学号是键，姓名是值：

```cpp
skipList<int, std::string> students(16, 0.5, 42);
students.insert({1002, "Li"});
students.insert({1001, "Wang"});
students.insert({1002, "Liu"}); // 更新已有值，不增加元素个数。
auto entry = students.find(1002);
if (entry != nullptr)
    entry->second = "Chen";
students.erase(9999); // 不存在的键：不做任何事。
```

`dictionary.hpp` 定义本章共同的接口：

| 操作 | 含义 |
| --- | --- |
| `empty()` | 是否没有数对 |
| `size()` | 数对个数，接口返回 `int` |
| `find(key)` | 返回数对指针；未找到返回 `nullptr` |
| `contains(key)` | 通过 `find` 判断键是否存在 |
| `insert(pair)` | 新增键；若键已存在则更新值 |
| `erase(key)` | 删除指定键；不存在则保持不变 |

五种实现都继承 `dictionary<K, E>`，因此可以通过基类引用调用这些操作。`output`、`outputLevels`、`rehash` 等扩展功能不在基类接口中，要通过具体类型调用。基类析构函数是虚函数，支持通过基类指针正确析构派生对象。

### 为什么是 `std::pair<const K, E>`？

- `first` 是键，不能直接修改：改键会破坏有序关系，或让元素落在错误的哈希桶中。
- `second` 是值，可以修改。改变键应当先删除旧数对，再插入新数对。
- 本章沿用的 `find(const K&) const` 返回可修改的数对指针。因此即使通过 `const` 容器引用查找，也可以修改值；这是教学接口的约定，不等同于标准容器的 const 迭代器语义。
- 指针不拥有数对，不应对它调用 `delete`。先判空，再解引用。

各实现都能保存没有默认构造函数的键和值；需要复制容器时相应类型须可复制，更新已有值时 `E` 须可赋值。调用输出功能还需要键和值支持流输出。

## 2. 从有序数组、有序链表出发

- `sortedArrayList.hpp`：按键排序，二分查找定位。插入和删除可能移动后面的元素，所以不能把二分查找的 `O(log n)` 当成插入总成本。
- `sortedChain.hpp`：按键排序，但单链表不能直接跳到中点。查找位置需要顺序前进；找到前驱后，链接或摘除结点本身是常数时间。

两者以及跳表使用 `<` 判断顺序。键等价的含义为 `!(a < b) && !(b < a)`，不要求提供 `operator==`。`<` 必须满足严格弱序，不能随意写成不一致的比较规则。

例如按键插入 `(30,C),(10,A),(20,B)` 后，两种实现的逻辑顺序都是 `10→20→30`。有序数组把数对指针连续放在数组槽位：查找 20 可二分定位，向最前面插入新键仍要右移后面的指针；`pair<const K,E>` 的键不能被赋值，所以实现移动**指针**，不覆写键。单链表则保存带 `next` 的数对结点：找到插入前驱后只改链接，但为了找到前驱，仍需从头顺序扫描。

| 有序线性表 | 查找位置 | 已知位置后的局部修改 | 完整插入／删除 |
| --- | --- | --- | --- |
| 有序数组 | 二分 `O(log n)` | 后缀移动最坏 `O(n)` | 最坏 `O(n)` |
| 有序单链表 | 顺序扫描 `O(n)` | 改链接 `O(1)` | 最坏 `O(n)` |

二者都按键升序输出，且 `insert` 已有键时只更新值。比较它们时，必须把“定位”和“修改”两段成本相加。

## 3. 跳表：给有序链表加上多层“快速通道”

`skipList.hpp` 的最底层保存所有数对并按键递增；上层只包含部分结点。一个结点越高，就越有机会让搜索一次跳过多个底层结点。下面仅是结构示意，并非种子 42 的固定输出：

```text
高层：head ----------------> 30 ----------------> 70
中层：head ------> 10 ------> 30 ------> 50 ------> 70
底层：head -> 5 -> 10 -> 20 -> 30 -> 40 -> 50 -> 60 -> 70
```

### 随机晋升

新键至少进入底层。以概率 `p` 继续向上一层晋升，直到晋升失败或达到 `maxLevel`。例如 `p = 0.5` 时，高层结点的期望数量逐层减少。随机化用于避免手动维护严格平衡，不意味着搜索过程随机选择路径。

**理想层次为何接近对数？** 若第 0 层有 `n` 个结点，第 `ℓ` 层的期望结点数约为 `n p^ℓ`。当 `p=1/2` 时示意数量是 `n,n/2,n/4,...`；到大约 `log₂ n` 层时只剩常数个结点。查找在高层跨过大段底层位置，再逐层下降；每层的期望水平步数与 `1/p` 同阶，因此在层数足够时，查找、插入定位和删除定位的期望时间为 `O((1/p)log_{1/p} n)`。这说的是随机高度分布下的**期望**，不是每次调用的确定上界。

```cpp
skipList<int, std::string> data(16, 0.5, 42);
```

三个参数依次是最大层数、晋升概率、随机种子。`maxLevel >= 1`，概率必须严格位于 `(0, 1)`，否则抛出 `std::invalid_argument`。`maxLevel = 1` 合法，但退化为普通有序链表。

默认种子来自 `std::random_device`。演示和测试显式使用 42，便于同一实现下重复运行。不同标准库的随机分布实现可能不同，不应把具体层形状当成跨平台保证。

### 查找：先右移，再下降

1. 从最高有效层的头部开始。
2. 只要下一个结点的键仍小于目标，就向右走。
3. 不能继续右移时下降一层，保留已经走过的位置。
4. 到底层后，检查后继是否与目标键等价。

例如查找 40，可先沿高层到 30，再逐层下降，而不是从底层的 5 开始逐个访问。

### 插入：记录每层前驱

搜索时把每层停下来的位置记录在 `update` 前驱数组中。

- 如果底层后继的键已存在，只更新 `second`。
- 如果是新键，生成随机高度；对新结点参与的每一层，把它接到对应前驱后面。
- 若新高度超过当前有效高度，新增层的前驱是头部入口。

`update` 表示“每层需要改哪条链接”，不是复制一份元素。头部可以用每层的入口指针表示，不需要构造一个特殊的最大键或最小键数对。
每个新结点持有长度等于自身高度的 `next` 指针数组；只在这些层上改前驱与新结点的链接。当前实现先分配新结点，再改链接，避免分配失败后留下半插入状态。

### 删除：用同一组前驱绕过目标

同样先搜索并记录各层前驱，在目标参与的每层将前驱链接改指向目标的后继，再释放目标结点。若最高层已空，降低有效层数；空表也保留一个有效底层，所以 `levels() >= 1`。
若目标不存在，不应删除“下一较大键”；先比较候选键是否等价，再动链接。单个结点的期望指针数是 `1+p+p²+... = 1/(1-p)`，因此固定 `p<1` 时全部结点的期望指针空间为 `O(n)`，另有 `O(maxLevel)` 的头部与搜索前驱数组。

- `output(out)`、`operator<<`：沿底层按键升序输出 `key value\n`。
- `levels()`：当前有效层数，不是构造时指定的最大层数。
- `outputLevels(out)`：逐层展示索引结构，适合观察晋升与删层。

## 4. 哈希表：先算桶，再在桶里找键

散列函数 `Hash(key)` 把键映射到一个整数，再由 `Hash(key) % m` 定位到 `m` 个桶／槽之一。不同键可能得到相同位置，这叫**碰撞**；只要键的可能取值多于桶数，碰撞就无法完全避免。必须满足：`KeyEqual(a,b)` 为真时 `Hash(a)==Hash(b)`，且已存键的散列结果不能在容器生命期中随意改变，否则查找会走错位置。反过来哈希值相等**不能**证明键相同，仍需 `KeyEqual` 核对。

`hashFunctions.hpp` 给出逐字节混合字符串的 `Fnv1aStringHash`，可用于复现实验；它不是密码学散列，不保证抵抗恶意构造的碰撞。表会对结果取模，因此更换桶数可能改变位置。好的散列分布与合理负载因子通常比“计算哈希很快”更重要；若所有键都落在同一桶，散列表会退化。

`hashTable.hpp` 使用链地址法（separate chaining）：桶数组的每个位置保存一条链表的入口。通常先计算 `Hash(key)`，再按桶数映射到桶下标。

```text
桶 0 -> (10, A) -> (30, C)
桶 1 -> 空
桶 2 -> (20, B)
```

不同键可能进入同一个桶，这叫碰撞。碰撞不表示键相等，也不应该覆盖别的键：在目标桶的链表中，用 `KeyEqual` 确认是否是同一个键。

```cpp
hashTable<int, std::string> data(11, 0.75);
```

参数依次为初始桶数、最大负载因子，可继续传入自定义哈希与判等对象。

- 初始桶数必须大于 0。
- 最大负载因子必须是有限正数；链地址法允许它大于 1。
- 判等为真的键必须产生相同哈希值，否则查找可能走到不同桶。
- 哈希表不要求键有 `<`；默认使用 `std::hash<K>` 和 `std::equal_to<K>`。自定义键可以显式传入匹配的两个函数对象。
- 为保证复制赋值时策略和桶能安全地一起替换，本实现要求两个函数对象都支持不抛异常的 `std::swap`，并用 `static_assert` 检查。它们的散列计算或判等调用本身仍可以抛异常。

`dictionaryDemo.cpp` 的 `ConstantHash` 故意把所有键映射到同一桶。这样可以观察：即使严重碰撞，正确性也应保持，只是性能退化。

### 负载因子与 rehash

负载因子 `alpha = 元素个数 / 桶数`，对应 `loadFactor()`。`bucketCount()` 返回桶数。

新增元素导致负载过高时，容器扩充桶数组，再将已有结点按新桶数重新链接，即 rehash。更新已有键不增加元素个数。

```cpp
data.rehash(23); // 请求至少 23 个桶，同时必须满足最大负载约束。
```

`rehash(0)` 抛出 `std::invalid_argument`。请求太小时，实际桶数会向上调整到至少能容纳当前元素的数量，而不是盲目使用请求值。rehash 改变的是桶和链接，不是键本身，也不能修复一个总返回相同值的糟糕哈希函数。

哈希输出按桶和桶内链表遍历，**不保证按键排序**，rehash 后遍历顺序也可能改变。测试应比较数对集合，而不是假设固定输出顺序。

### 线性探查：冲突后继续看下一个槽

`linearProbingHashTable.hpp` 实现开放寻址的经典方法。若初始槽位 `h(k)=Hash(k)%m` 被占，就依次检查 `(h(k)+1)%m`、`(h(k)+2)%m` 等位置。每个槽位有三种状态：**Empty**（从未占用）、**Occupied**（存有数对）、**Deleted**（曾有数对，现已删除的“墓碑”）。

假设 `m=7`，三个键的初始槽位都是 3：

```text
插入 10、17、24：槽 3=[10]，槽 4=[17]，槽 5=[24]
删除 17：       槽 3=[10]，槽 4=Deleted，槽 5=[24]
查找 24：       从槽 3 开始，跨过槽 4 的墓碑，到槽 5 才找到。
```

**为何不能把槽 4 改成 Empty？** 查找遇到 Empty 可以确定这条探查链结束；若删除 17 后槽 4 变成 Empty，24 明明还在槽 5 却会被误判不存在。插入新键时可以记住探查过程中第一个墓碑，继续确认后方没有同键，再优先复用它。

线性探查表的负载因子 `α=n/m` 必须严格小于 1，至少保留空槽让失败查找终止。代码限制最大负载因子在 `(0,1)`；插入使它过高时扩容重散列，墓碑过多时用同等容量重散列清理墓碑。相邻占用槽会形成**聚集（clustering）**，后续键更可能加入长探查段；因此开放寻址通常比链地址法更在意负载因子。`tombstones()` 可以帮助观察删除后的状态。

两种实现的核心区别：链地址法在桶外接一条结点链，`α` 可以大于 1，但每个结点有指针和分配开销；线性探查在槽数组内向后试，常有较好的连续访问局部性，但墓碑和聚集使探查变长。这里线性探查的数对由 `unique_ptr` 独立持有，槽位移动不移动数对本身，所以 `rehash` 后已有数对指针保持有效；这是**本教学实现**的承诺，不要推断所有开放寻址容器都有此特性。删除对应键仍会使该指针失效。

## 5. 复杂度：不要混淆期望、均摊和最坏情况

下表把键比较、哈希计算、值复制等单次操作视为 `O(1)`；昂贵的键和值会增加实际成本。`n` 是数对个数，`m` 是桶数。

| 实现 | 查找 | 插入新键 | 删除 |
| --- | --- | --- | --- |
| 有序数组 | `O(log n)` | 最坏 `O(n)` | 最坏 `O(n)` |
| 有序链表 | 最坏 `O(n)` | 最坏 `O(n)` | 最坏 `O(n)` |
| 跳表 | 通常期望 `O(log n)` | 通常期望 `O(log n)` | 通常期望 `O(log n)` |
| 链地址哈希表 | 分布良好时平均 `O(1 + alpha)` | 通常均摊 `O(1)` | 分布良好时平均 `O(1 + alpha)` |
| 线性探查哈希表 | 分布良好且 `alpha<1` 时平均 `O(1)` | 通常均摊 `O(1)` | 分布良好时平均 `O(1)` |

- 跳表的对数期望需要合理的固定晋升概率与足够的高度上限。固定 `maxLevel` 后，不能对无限增长的 `n` 无条件声称对数复杂度；高度太低会使高层仍有很长的水平遍历。最坏会线性扫描；若也把最大层数 `L` 当变量，保守界还需计入层下降和指针维护的成本，如 `O(n + L)`。
- 哈希表的平均常数时间依赖哈希分布和受控负载因子；所有键落入一桶时，链地址法可能扫描 `O(n)` 个结点，线性探查可能扫描 `O(m)` 个槽位。自动扩容使一次插入明显较慢，不能说每次插入都严格 `O(1)`。线性探查的墓碑也会让失败查找变慢，所以需要周期性清理。
- 一次 rehash 通常要遍历数对并初始化新桶／槽，成本为 `O(n + m_new)`，不包含昂贵的用户哈希成本。反复手动要求巨大数组不受通常的均摊常数结论保护。
- 跳表在通常随机参数下每个结点的期望指针数为常数；两种哈希表还需要 `O(m)` 的桶／槽数组，链地址与本章开放寻址实现均另有 `O(n)` 的数对结点。

## 6. 应用：LZW 字典压缩

`lzw.hpp` 给出字节版 LZW 的**编码和解码**。这里的字典键不是单个字符，而是已经见过的字节短语；值是该短语的整数码。编码器用本章的线性探查表做“短语 → 编码”查询，解码器用数组做“编码 → 短语”查询。二者从相同的初始字典开始：单字节 `0..255` 对应编码 `0..255`，新短语从 256 起依次编号。

编码器维护当前最长已知短语 `w`，读取下一个字节 `c`：

1. 若 `w+c` 已在字典里，就让 `w=w+c`，继续尝试更长短语。
2. 若不在，输出 `w` 的编码；容量未满时把 `w+c` 加入字典；然后从单字节 `c` 重新开始。
3. 输入结束时，再输出剩余的 `w`。

例如 `ABABABA`（A=65、B=66）：

```text
输出 65，新增 AB→256
输出 66，新增 BA→257
输出 256，新增 ABA→258
输出 258
码流：[65,66,256,258]
```

**解码器怎样同步建字典？** 已知上一个解出的短语 `previous`，读到下一个短语 `entry` 后，新词条就是 `previous + entry 的首字节`。有一个容易漏掉的合法边界：码流可能引用解码器**即将**建立的下一个编号，此时 `entry = previous + previous 的首字节`，常称 `KwKwK` 情况；上面的 `258` 就会触发它。其他超出字典范围的编码必须报错。编码和解码必须使用相同的 `maxCodes`；达到上限后两边都停止新增词条，不清表。

本示例返回 `std::vector<int>` 码流，**没有**实现可变位宽打包、文件格式头或清表控制码。因此不能仅因码流整数个数少于输入字节数，就断言输出文件实际更小；短输入甚至可能更大。测试覆盖空串、全部 256 个字节、重复短语、小字典容量以及含零字节的随机输入。若把字符串拼接、复制与存储也算入，耗时和内存依赖实际短语长度，不应只凭一次散列表查询的平均常数时间声称整个压缩必为 `O(输入字节数)`。

## 7. C++ 实现阅读提示

### `std::vector` 在这里做什么？

跳表和两种哈希表不是 `std::map` 或 `std::unordered_map` 的包装。它们自行实现结点、搜索、探查与链接。`std::vector` 用于跳表层头、结点前向指针、链地址桶入口、开放寻址槽数组和 LZW 解码数组，不代替关键的字典算法。测试中的 `std::map` 只充当独立的正确性参照。

### 模板为什么写在头文件里？

编译器实例化 `skipList<int, std::string>` 时通常需要看见模板定义，因此模板类及其成员定义放在 `.hpp` 中。头文件需要包含保护，防止同一翻译单元重复定义；这不能代替非模板自由函数的 `inline` 规则。普通演示、测试函数放在各自的 `.cpp` 中。

```cpp
typename skipList<K, E>::value_type*
```

这里的类型依赖模板参数，`typename` 告诉编译器 `value_type` 是类型名。`override` 则要求编译器检查某个成员是否正确覆盖了基类虚函数，避免签名拼错后悄悄定义一个新函数。

### 拷贝与指针有效期

跳表与两种哈希表都支持深拷贝构造和赋值：修改或删除副本中的元素不影响原件，也支持自赋值。

跳表插入、链地址哈希表插入与 rehash 不移动已有数对；本章线性探查表以独占指针保存数对，rehash 也不移动数对，因此这些操作后已有数对指针保持有效。删除某个键后，指向该数对的指针立即失效；容器析构或被赋值后，不应再使用原来保存的指针。不要把这一保证推广到任意字典实现，或把失效指针拿来解引用测试。
